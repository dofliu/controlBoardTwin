日期：2026-10-23（台北）。狀態：第 1 階段（V2.8）、第 2 階段（V2.9）、第 3 階段（V2.10，2026-10-24）、第 4 階段（V2.11）、第 5 階段（V2.12，2026-10-24）**已實作**，已在虛擬設備驗證，未以實體設備驗證；第 6–7 階段仍是**設計提案**。
標示沿用專案的四種：**已確認需求**、**設計提案**、**已實作**、**未驗證**。

## 0. 需求（已確認需求）

使用者 2026-10-23 提出：

> 假設沒有硬體，但想要驗證：能不能在另外一個地方（雲端）建立一個虛擬硬體，讓介面假裝去連線，一樣可以交換資料，達到數位孿生的目標（當然實際上還是需要硬體）。

翻成要做到的事：

1. 介面連線時，對方是**另一台機器上的另一個程式**，資料真的經過網路，不是同一個網頁裡的假物件。
2. 數位孿生的整條路徑都要跑過：辨識 → 唯讀觀測 → 核對接線 → 授權受控寫入 → 命令 → 回讀 ACK → 量測 → 過期 → 斷線 → 重連（不重送）。
3. 任何畫面、紀錄、文件都要清楚標示「虛擬設備」，不能讓人以為是實體設備驗證過。

## 1. 能驗證什麼、不能驗證什麼

| 虛擬設備**能**驗證 | 虛擬設備**不能**驗證（仍需實體） |
|---|---|
| 介面 ↔ 設備的協定（Firmata、pi_bridge）每一個位元組 | 電壓、電流、接觸不良、雜訊等真實電氣 |
| 數位孿生五層狀態在網路延遲、掉包、斷線下的行為 | SG90 的實際速度、負載、抖動、到不了位 |
| 韌體本身（Uno：跑的是真的 DofLabFirmata 機器碼） | ESP32 真實韌體（目前沒有可用的模擬器，見 §8） |
| 產生的程式在晶片上的邏輯與時序（Uno） | 觸控門檻、超音波對實際物體的回波 |
| 多人同時觀看、控制權、紀錄與重播 | USB 驅動、作業系統序列埠、瀏覽器權限 |

## 2. 設計原則

1. **協定和實體一樣，只換傳輸層。** 介面送出的 Firmata 位元組、pi_bridge 的 JSON，和接實體板子時完全相同；差別只在「USB 序列埠」換成「WebSocket」。這樣虛擬設備驗證過的程式碼，就是接實體板子時跑的程式碼。
2. **虛擬設備獨立於介面。** 它是另一個程序：有自己的時鐘、自己的電路與物理模型、自己的接線表。輸入（按按鈕、調亮度、放物體）來自介面以外的「工作台」頁面或腳本。
   - 為什麼：如果虛擬設備和介面共用同一份模擬引擎，兩邊一定一致，等於自己驗證自己。工作台的電路與物理模型要**另外寫**，不重用 `src/core/engine.js`。
3. **永遠標示為虛擬。** 辨識回應帶 `kind: "virtual"`；介面的模式標籤、孿生狀態表、事件紀錄、狀態表都顯示「虛擬設備」。
4. **先在本機跑通，再上雲端。** 第 1–5 階段全部在 `localhost` 完成；要不要放到雲端、放在哪裡，是使用者的決定（§9）。

|---|---|---|---|

| DofLabFirmata 1.1 | `tools/firmware/DofLabFirmata/`、`tests/fixtures/DofLabFirmata-uno.hex` | 真機同步 | 虛擬 Uno 預設跑這個韌體 |

**實測數據**（2026-10-23，雲端容器、單一 CPU 核心）：虛擬 Uno 跑 DofLabFirmata，3000 ms 的晶片時間用了 1242 ms 的實際時間，約 **2.4 倍即時**。avr8js 即使韌體閒置也要逐週期模擬，所以**一個 CPU 核心大約只能同時跑 2 台即時的虛擬 Uno**。這會決定雲端主機的大小（§9）。

## 4. 架構（設計提案）

```
 ┌──────────────── 使用者的瀏覽器 ────────────────┐        ┌──────────── 虛擬設備主機（先本機，之後可上雲端） ────────────┐
 │ DofLab（觀測頁）                                │        │  vdev 閘道（Node，tools/vdev/server.js）                       │
 │   FirmataDriver ── WebSocketTransport ─────────┼─ wss ─▶│    ├─ 設備 uno-1：avr8js 跑 DofLabFirmata.hex                   │
 │   PiBridgeDriver ──────────────────────────────┼─ wss ─▶│    │     └─ 工作台 bench：接線表＋按鈕彈跳、光敏雜訊、          │
 │                                                 │        │    │         超音波回波、伺服脈寬→角度（只顯示，不回報）      │
 └─────────────────────────────────────────────────┘        │    ├─ 設備 uno-2 …（每台一個 worker thread）                   │
 ┌──────────── 工作台頁（另一個分頁或另一個人）────────────┐   │    └─ 控制權、紀錄、故障／網路注入                          │
 │ /bench：按按鈕、調亮度、放物體、拔線、斷電、看 LED／伺服 ┼──▶│  pi_bridge.py --mock --bench（虛擬樹莓派）                    │
 └─────────────────────────────────────────────────────────┘   └───────────────────────────────────────────────────────────────┘
```

### 4.1 傳輸層：Firmata 位元組走 WebSocket

- `FirmataDriver` 改成接受一個傳輸物件，介面固定為：`open()`、`onBytes(cb)`、`write(bytes)`、`setSignals({dataTerminalReady, requestToSend})`、`close()`、`info()`。
  - `WebSerialTransport`：包裝現在的 Web Serial 程式碼，包含 V2.6.1 的占用處理（`DL.serial`）。
  - `WebSocketTransport`：二進位訊框＝序列埠位元組；文字訊框＝控制訊息（JSON）。
- 控制訊息（文字訊框）：
  - `→ {"op":"hello","client":"doflab","proto":1}`
  - `← {"op":"hello","kind":"virtual","board":"uno","device":"uno-1","firmware":{"name":"DofLabFirmata","sha256":"…"},"bench":"bench-a","clock":"virtual"}`
  - `→ {"op":"signals","dtr":false,"rts":false}`：對應 DTR／RTS，讓「板子沒回應時重新啟動」與 STK500 上傳照常運作
  - `→ {"op":"lock","want":"control"}`／`← {"op":"lock","holder":"…","you":true}`：控制權（§4.5）
  - `← {"op":"event","kind":"reset"|"brownout"|"unplugged"|"bench", …}`：工作台事件，只當作紀錄，不當作量測
- 介面：「觀測」頁的「真機連線」多一個來源選項「**虛擬設備（網址）**」，填 `ws://localhost:8770/dev/uno-1` 或雲端網址加上通行碼。
- 附帶好處：不需要 Web Serial，所以手機與 Safari 也能連虛擬設備。

### 4.2 辨識與標示

- `connect()` 的 `identity` 帶入 `kind: "virtual"`；`twin.connected(deviceId, info)` 的 `deviceId` 用 `vdev:uno-1@主機`。
- 模式標籤：「虛擬設備 · 唯讀」「虛擬設備 · 受控寫入」，顏色和實體設備不同。
- 孿生狀態表的量測欄寫「量測（虛擬）」；事件紀錄、匯出的紀錄檔都帶 `virtual: true`。
- 版本狀態表、ACCEPTANCE 的用語：「已在虛擬設備驗證」，**不寫**「已驗證」。

### 4.3 虛擬工作台（bench）：設備外面的世界

工作台定義「這台虛擬板子實際接了什麼」，格式建議沿用專案檔的接線表（`bench.json`），但**電氣與物理模型另外實作**：

| 元件 | 工作台模型（教學假設，參數可調） | 介面能看到什麼 |
|---|---|---|
| 按鈕 | 按下時拉低腳位；按下與放開各有 0–8 ms 的隨機彈跳 | 量測層的按下／放開（考驗去彈跳） |
| LED | 讀腳位電位與限流電阻 → 亮度與電流；超過 20 mA 標示警告 | 工作台上的 LED（介面的 ACK 只是回讀暫存值） |
| 光敏模組 | 亮度 → 電壓，加 ±1 % 雜訊；avr8js 的 ADC 做 10 位元量化 | 量測層的亮度 % |
| 超音波 | 依距離產生回波時序；可設定掉回波的機率 | 量測層的距離 |
| SG90 | 從腳位的高電位寬度算出命令角，再以有限速度轉到該角度 | **只在工作台顯示**；不回報給量測層（SG90 本來就沒有回授） |
| 觸控（ESP32） | 先不做（§8） | — |

工作台也要能做到「**接線和專案不一致**」：例如專案寫 LED 接 D13，工作台實際接 D12。這時候「核對接線」那一步應該發現「按了按鈕沒變化」或「LED 命令有 ACK，但工作台上的 LED 沒亮」。這正是實體教學最常見的錯誤，虛擬設備可以安全地重現。

### 4.4 故障與網路注入

每一種故障都對應數位孿生應有的反應，可以直接寫成驗收測試：

| 注入 | 數位孿生應有的反應（現有規則） |
|---|---|
| 延遲 200 ms ± 100 ms | 量測與 ACK 延後，但順序正確；序號去重 |
| 掉包 5 % | 逾時未確認的命令標示出來，不自動重送 |
| 連線中斷 | 回到模擬；未確認命令作廢、不重送；量測標為過期 |
| 設備重置／瞬間斷電 | 偵測到重新開機（Firmata 重新送版本）→ 撤銷寫入授權，回到唯讀 |
| 感測器卡住（數值不再更新） | 超過 `staleMs` 標為過期 |
| 工作台拔掉一條線 | 唯讀觀測看得到「沒有變化」；核對接線失敗 |

### 4.5 多人與控制權

- 一台虛擬設備可以有多個連線：老師、助教、學生都能**唯讀觀看**同一台。
- 「授權受控寫入」＝向閘道取得**唯一的控制權**；其他人在畫面上看到「控制中：○○」。控制權在中斷、逾時或撤銷時釋放。
- 這也是實體教室要的功能：一台設備接在老師電腦上，全班一起看。

### 4.6 時間

- 虛擬設備的時間是晶片週期，以 1 倍速對齊實際時間；回報帶設備時間戳。
- 介面用「收到時間」判斷過期，用 `ping`／`pong` 量網路來回時間並顯示。
- 可以提供 0.25 倍、0.1 倍慢動作，給教學用；慢動作時標示「時間非即時」。

### 4.7 上傳程式到虛擬設備

- 「程式」頁的上傳多一個目標「虛擬 Uno」：透過 WebSocket 傳 STK500 位元組給虛擬 Optiboot（`tests/upload_avr.test.js` 已經在 Node 裡驗證過這條路）。
- 上傳後板子跑的是**使用者產生的程式**，工作台顯示 LED／伺服；USART 的文字（`Serial.println`）串流回介面的序列埠監看。
- 想同步時再上傳 DofLabFirmata，和實體板子的操作完全一樣。

## 5. 安全與部署（設計提案）

- **預設只在本機**：`node tools/vdev/server.js` 只聽 `127.0.0.1:8770`。
- **docker compose**：`vdev` 一個容器；`pi_bridge --mock` 一個容器。
- 放到雲端時至少要有：
  - `wss://`（TLS）；每個工作階段一組通行碼；沒有通行碼一律拒絕。
  - 每台虛擬設備限制 CPU 與記憶體；閒置 10 分鐘自動關閉。
  - 上傳的韌體只在模擬器裡執行，不會在主機上執行；**pi_bridge 的「部署 Python 程式」功能在雲端必須關閉，或放進隔離的容器**，否則等於讓任何人在主機上執行程式。
  - 紀錄保存多久、記錄哪些資訊，要先決定（學生資料）。

### 第 1 階段實作紀錄（V2.8，2026-10-23）

- 做了：`tools/vdev/server.js`（只聽本機、一台 `uno-1`、每台一個 worker thread）、`device.js`、`bench.js`（按鈕＋LED，不用 engine.js）、`src/drivers/transport.js`（`WebSerialTransport`、`WebSocketTransport`）、觀測頁的來源「虛擬設備（網址）」與各處的虛擬標示、`tests/vdev.test.js`（4 項）、E2E 段落 `vdev`（14 項）。`VirtualUno` 已搬到 `tools/vdev/avrsim.js`。
- 和本文件原本設計不同的地方：
  - 第 1 階段先用 HTTP API（`/api/devices/uno-1`、`/bench`）與一頁簡易工作台操作按鈕；完整的 `/bench` 頁仍在第 2 階段。
  - 同時只接受一個連線（第 2 個連線會收到 `busy`）；§4.5 的多人唯讀觀看與 `lock` 控制訊息留到第 5 階段。
  - 預設網址用 `ws://127.0.0.1:8770/dev/uno-1`（不用 localhost：瀏覽器可能先試 IPv6 的 ::1，而主機只聽 127.0.0.1）。

  - 虛擬樹莓派沒有用 hub.js 的控制權：pi_bridge 本來就依腳位分配（同一個腳位同時只有一個連線能用）。

- 發現（**設計提案**，待使用者決定）：
  - （2026-10-25 使用者決定統一成 544–2400 µs，**已實作**）同一個角度命令，樹莓派與 Uno／ESP32 送出的脈寬不同：pi_bridge 用 gpiozero `AngularServo` 500–2400 µs，Arduino Servo 函式庫 544–2400 µs。0° 差 44 µs（約 4°），90° 差 22 µs（約 2°），180° 相同。同一顆 SG90 換板子會差幾度；要不要統一需要使用者決定。
  - （2026-10-25 使用者決定授權時先送目前的角度，**已實作**）授權受控寫入（伺服 attach）後、第一個角度命令到達前，Uno 與 ESP32 的韌體輸出 Servo 函式庫預設的 1500 µs（約 93°）；虛擬 Uno 的真韌體也是 1502 µs。伺服會先轉到中間，命令到了才轉回去（樹莓派不會：`initial_angle=None`）。
- 過程中發現並修正：協定模型的超音波偶爾停止量測（「距離警示」重跑 8 次有 3 次）：喚醒的排程因四捨五入比預定時間早一點點，量測迴圈就停了；改成進位；gpiozero 模擬腳位設上拉時會把電位拉回高，工作台要再設一次按鈕的電位。

## 8. ESP32 怎麼辦

avr8js 只模擬 AVR（Uno）。ESP32 的選項：

| 選項 | 優點 | 缺點 | 建議 |
|---|---|---|---|
| A. 協定模型（Node 寫一個「行為和 DofLabFirmata 一樣」的 ESP32） | 馬上可做；ESP32 的腳位圖、BOOT、藍燈、觸控都能模擬 | 跑的不是真的韌體，只驗證介面與協定 | **已實作**（V2.13，`tools/vdev/esp32model.js`），標示「協定模型，不是實際韌體」；觸控未做 |
| B. Espressif 的 QEMU 分支 | 跑真的 ESP32 機器碼 | GPIO、LEDC（伺服 PWM）、觸控的支援有限，需要先試 | 做一個小實驗再決定 |
| C. 商用線上模擬服務 | 支援度高 | 需要帳號，可能要付費；資料在第三方 | 由使用者決定，不列入預設 |

## 9. 需要使用者決定的事

1. 雲端放在哪裡（學校主機、自己的 VM、其他）；需要的帳號與費用。專案規則預設「不建立新帳號、不呼叫付費服務、不公開部署」，要改就由使用者明確說。
2. 一次要同時跑幾台虛擬設備：一個 CPU 核心約 2 台虛擬 Uno（§3 的實測），30 人的班級約需 15 個核心，或改成「老師一台、全班唯讀觀看」。
3. 學生是否從校外連線（決定通行碼與紀錄政策）。
4. 在你自己電腦上的 Claude Code 工作階段裡，是否允許 Claude 操作真實設備（例如上傳到你指定的 ESP32）。沒有明確同意前，維持「不操作真實設備」。
